## 2025-05-15 - JWT 'none' Algorithm Signature Bypass
**Vulnerability:** The `jwt::decode` method explicitly included `'none'` in its whitelist of supported algorithms. This allowed an attacker to bypass signature verification by providing a JWT with `alg: none`, potentially leading to authentication bypass or privilege escalation if the claims are trusted without verification.
**Learning:** Even when using a whitelist, including insecure defaults like `'none'` can negate the security benefits of the whitelist. In an authentication plugin, trusting the `id_token` claims without either signature verification or a secure back-channel is a high-risk pattern.
**Prevention:** Always remove `'none'` from JWT algorithm whitelists in production code. Ensure that JWTs are either verified cryptographically or received through a trusted back-channel where the source is authenticated.

## 2025-05-15 - PHP Object Injection via Unserialize
**Vulnerability:** The `unserialize()` function was used on data from the `auth_azureb2c_state` table without restricting allowed classes. If an attacker could influence the `additionaldata` stored in the state (e.g., through a separate vulnerability or database access), they could trigger PHP Object Injection.
**Learning:** Data stored in the database, even if originally generated by the application, should be treated with caution when being unserialized, especially if it represents state that can be manipulated or if the application has long-lived state records.
**Prevention:** Use `['allowed_classes' => false]` with `unserialize()` unless objects are explicitly required. Prefer JSON for serializing data when possible.

## 2025-05-15 - Missing Security Guards in PHP Files
**Vulnerability:** Many PHP files in the plugin lacked the `defined('MOODLE_INTERNAL') || die();` check. This could allow direct access to these files, potentially leading to information disclosure or execution of code in an unintended context if global variables or environment state can be manipulated.
**Learning:** Moodle's security model relies on this check to ensure that files are only included within the Moodle environment. Missing it is a common compliance and security issue in Moodle plugins.
**Prevention:** Always include `defined('MOODLE_INTERNAL') || die();` at the top of every PHP file in a Moodle plugin, except for primary entry points that include `config.php`.
